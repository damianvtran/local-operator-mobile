# ADR 0004 — Build and release pipeline

- **Status:** Proposed (for implementation)
- **Date:** 2026-09-29
- **Deciders:** Local Operator Mobile maintainers
- **Depends on:** [ADR 0001 — Framework](0001-framework.md), [ADR 0003 — E2E and audit harness](0003-e2e-and-audit-harness.md)

## Context

The repository cannot build natively on the primary development machine — no
Xcode, no Android SDK, and installing them is explicitly out of scope
(`AGENTS.md`, "Build host assumptions"). **CI is therefore the only place the
native apps are built, tested, signed and published.** That makes the pipeline part
of the product, not plumbing: if the pipeline is wrong, the app cannot ship at all.

The pipeline also has to satisfy three external requirements that are newer than
most mobile CI templates:

- **Apple:** since **2026-04-28**, apps uploaded to App Store Connect must be built
  with **Xcode 26 or later against the iOS 26 SDK**
  ([developer.apple.com/news/upcoming-requirements](https://developer.apple.com/news/upcoming-requirements/),
  read 2026-09-29).
- **Google:** since **2026-08-31**, new apps and updates must target **Android 16
  (API 36)** ([support.google.com](https://support.google.com/googleplay/android-developer/answer/11926878),
  read 2026-09-29), and since 2025-11-01 they must support **16 KB page sizes**.
- **Repositories:** public, MIT, and a mix of maintainers and coding agents — so
  signing material must never be reachable from a fork pull request, and the
  version scheme has to be derivable from git rather than remembered.

### What the pipeline must produce

| Trigger | Artefacts |
|---|---|
| Pull request | lint/type/unit results, web export, mock-relay visual + a11y report, iOS simulator build result, Android debug APK, Maestro screenshots |
| Push to `main` | the same, plus a signed **internal** Android build and an **internal TestFlight** upload when the version changed |
| Tag `v*` | signed **AAB + APK** on a GitHub Release, **IPA** uploaded to TestFlight, **AAB** uploaded to the Play **internal** track |

## Decision

**GitHub Actions is the build system, `fastlane` is the store uploader, and Expo's
EAS services are optional accelerants rather than a dependency.**

### Why GitHub Actions rather than EAS Build as the primary

EAS Build is the easiest way to build an Expo app without a Mac, and we will keep
it documented as an escape hatch. It is not the primary because of the free tier's
shape: **15 Android and 15 iOS builds per month on a low-priority queue with a
single concurrency and a 45-minute timeout**, against paid builds at $1 (Android)
and $2 (iOS) per build
([expo.dev/pricing](https://expo.dev/pricing), read 2026-09-29). A pipeline that
builds on every push would exhaust that in days, and the 90-minute peak queue is
incompatible with "the PR tells you within the hour". GitHub-hosted runners are
**free for standard runners in public repositories**
([docs.github.com](https://docs.github.com/en/actions/concepts/billing-and-usage),
read 2026-09-29), which makes our scarce resource **wall-clock and concurrency**,
not money — and that is a budget we can actually design around. The macOS image
`macos-26` is generally available and ships Xcode 26.x, which satisfies Apple's
current requirement ([github.blog changelog](https://github.blog/changelog/2026-02-26-macos-26-is-now-generally-available-for-github-hosted-runners),
read 2026-09-29).

### Why `fastlane` rather than EAS Submit

`fastlane` runs *in the same job that produced the artefact*, with the App Store
Connect API key and the Play service account held by GitHub secrets, and it does not
require an Expo account, an EAS project, or re-uploading a build. It also gives us
direct control of `versionCode`/`CFBundleVersion`, which matters for the versioning
rule below. EAS Submit remains a one-command alternative if we ever move builds to
EAS; nothing in the workflow depends on `fastlane` for anything but the upload step.

### Job graph

```
pull_request ─┬─ checks            (ubuntu)  biome · tsc · jest · expo export web
              │                              · headless-Chrome matrix + axe floor
              │                              → screenshots + report artefacts
              ├─ android           (ubuntu)  prebuild · gradle assembleDebug
              │                              → debug APK · emulator + Maestro
              └─ ios               (macos-26) prebuild · xcodebuild (simulator)
                                             → .app · simulator + Maestro

push main     ─┬─ every PR job, plus:
              └─ internal-release  (ubuntu + macos-26)
                                   → signed APK/AAB (internal) · TestFlight internal

tag v*        └─ release            (ubuntu + macos-26, environment: release)
                                   → GitHub Release (AAB, APK, IPA)
                                   → Play internal track · TestFlight
```

Notes that keep this honest:

- **Path filters must not strand required checks.** Native jobs are skipped when a
  change touches only `docs/**` or `**/*.md`. Because GitHub treats a skipped job as
  satisfied but *never runs* a workflow that a path filter excludes (which leaves a
  required check pending forever), the workflow always runs and the expensive jobs
  are gated with an explicit `if:` on a `changes` job that inspects the diff. This
  is a known trap and the reason the filter lives inside the workflow rather than in
  `on.paths`.
- **Concurrency group per ref**, `cancel-in-progress: true` for PRs and `false` for
  `main` — the same rule the sibling repository uses, because cancelling a run on
  `main` can cancel the run that was about to publish.
- **One retry**, only for the emulator/simulator flows, and the retry's output is
  kept separately so a flaky flow cannot be mistaken for a pass.
- **Least privilege:** workflow-level `permissions: contents: read`; the release job
  elevates to `contents: write` for the Release and is the only job in a
  `release` environment (which is where the store credentials live, and where
  required reviewers can be configured once there is more than one maintainer).
- **Fork PRs never see secrets.** GitHub does not pass repository secrets to
  `pull_request` runs from forks, so the signed-build steps are additionally gated
  on `github.event.pull_request.head.repo.full_name == github.repository`.

### Versioning

One source of truth: the **git tag**, `vMAJOR.MINOR.PATCH`.

| Value | Rule |
|---|---|
| `version` (JS/`app.json`) | the tag without `v`; on non-tag builds, `0.0.0-dev.<run_number>` |
| Android `versionCode` | `github.run_number` (monotonic across all builds of the repository, never reused) |
| iOS `CFBundleShortVersionString` | the tag without `v` |
| iOS `CFBundleVersion` | `github.run_number` |
| Release notes | generated from conventional commits since the previous tag |

The version is **never bumped in a pull request** — a maintainer opens a dedicated
`chore(release): vX.Y.Z` pull request, or tags directly from `main` after CI is
green (the sibling repositories do the latter; this repository should follow the
tag-only rule and keep the version out of source files entirely, using `app.json`'s
`expo.version` as a dev placeholder). `versionCode`/`CFBundleVersion` derived from
`run_number` can never go backwards, which is the one property both stores enforce
at upload time.

### Caching and build-time budget

| Cache | Key | Notes |
|---|---|---|
| pnpm store | `pnpm-lock.yaml` hash | `actions/setup-node` with `cache: pnpm`; never `npm install`, never a copied `node_modules` (`AGENTS.md`) |
| Gradle | `gradle/actions/setup-gradle` (built-in caching) | plus the Android build cache directory; Expo's own recommendation |
| CocoaPods | `ios/Pods` + `~/.cocoapods` on `Podfile.lock` + Xcode version | only relevant if prebuild emits Pods; SDK 57 projects still use CocoaPods |
| Metro | `~/.expo` and `.expo` | small win, cheap to add |
| Android AVD | `~/.android/avd` keyed on the system image id | AVD creation is minutes; boot is seconds from cache |

`ios/` and `android/` are **not committed** — continuous native generation
(`expo prebuild`) is the source of truth, and the config plugins are what a reviewer
reads. A job asserts that `expo prebuild --clean` produces no diff against what CI
built, so a stale generated file can never be the thing that ships.

### Secrets inventory (names only, values never in the repository)

| Store | Purpose |
|---|---|
| `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` | release signing; keystore is base64 in a secret and written to a temp path at build time |
| `APPLE_TEAM_ID`, `APPLE_ASC_KEY_ID`, `APPLE_ASC_ISSUER_ID`, `APPLE_ASC_PRIVATE_KEY_BASE64` | Xcode automatic signing (`-allowProvisioningUpdates`) and `fastlane` uploads |
| `PLAY_SERVICE_ACCOUNT_JSON_BASE64` | Play internal-track upload |
| `EXPO_TOKEN` | **optional** — only if the EAS escape hatch is used |
| `MAESTRO_CLOUD_API_KEY` | **optional** — parallel native runs, if we ever outgrow one emulator |

Signing material for iOS is deliberately limited to an App Store Connect API key
plus automatic signing, so there is no certificate/profile to rotate by hand. The
Android keystore is the one artefact that, if lost, cannot be replaced by anything
but a new application id — its backup is a documented, offline maintainer
responsibility, and the README should say so plainly.

### Stores and distribution channels

| Channel | v1 | Notes |
|---|---|---|
| App Store / TestFlight | yes | iOS 26 SDK build; TestFlight internal track from `main`, external when an IPA has been reviewed once. **Prerequisites that are not free and not automated:** a paid Apple Developer Program membership, and an App Store Connect app record with its bundle id registered before the first upload — the `APPLE_ASC_*` secrets below are useless without both. Signing is automatic (`xcodebuild -allowProvisioningUpdates`), so no certificate or profile is managed by hand |
| Google Play | yes | internal track first; target API 36; AAB; the 12-testers/14-day closed-test rule applies to **new personal** developer accounts, so an organisation account (with its D-U-N-S verification) avoids it |
| GitHub Releases | yes | signed APK + AAB + IPA attached; the place Android users who do not use Play get the app |
| AltStore / SideStore (iOS sideload) | later | needs the IPA and a user-supplied certificate; worth documenting, not worth automating |
| Obtainium / Accrescent (Android) | later | works off GitHub Releases once the signing-key fingerprint is published |
| F-Droid | **parked, with reasons** | F-Droid requires FOSS-only dependencies and builds from source: React Native's Android build resolves Maven artefacts and ships prebuilt native libraries (Hermes/JSI), and push notifications would pull in Google Play Services / Firebase. F-Droid has packaged React Native apps before with extra metadata, but it is a project of its own — a `foss` product flavour with notifications compiled out, an F-Droid build recipe, and a reproducible-build check. Revisit when notifications land, not before |
| Huawei AppGallery / others | no | revisit only if there is user demand |

### Over-the-air updates (planned, off at v1)

A client for a fast-moving relay benefits from shipping JavaScript fixes without
waiting for store review, so the plumbing (`expo-updates`) is designed in — but
**OTA is disabled in v1**, and turning it on is its own decision with the following
already written down:

- **Policy.** Apple's guideline **2.5.2** forbids downloading code that "introduces
  or changes features or functionality of the app"
  ([developer.apple.com/app-store/review/guidelines](https://developer.apple.com/app-store/review/guidelines/),
  last updated 2026-06-08, read 2026-09-29); Google's equivalent restricts
  executable-code download outside the app bundle. Over-the-air JavaScript that
  *fixes* an existing screen is fine under both; a new screen delivered by OTA is
  not. The rule we will adopt if OTA is enabled: OTA ships only JavaScript that was
  already reviewed as part of a shipped binary's feature set, never new capability,
  never a new native module, never a new permission.
- **Infrastructure.** `expo-updates` needs an update server: EAS Update on the free
  plan covers **1,000 monthly active users** with no overage option
  ([expo.dev/pricing](https://expo.dev/pricing), read 2026-09-29), which is fine for
  an early open-source app and a decision to revisit at scale; self-hosting
  `expo-updates`' protocol is possible but is infrastructure we would rather not own.
- **Security.** An update channel is a code-execution channel pointed at every
  installed app. It needs signed updates, a documented rotation for the code-signing
  key, and the same review gate as a release — not a `main`-branch auto-publish.
- **Rollback.** `expo-updates` supports rolling back to a previous bundle; the
  release runbook must name the command, because the first time it is needed is
  rarely the time to read the documentation.

Until that decision is taken, fixes reach users through TestFlight / Play internal
tracks, which is slower but has no policy surface.

**Reproducibility.** We will not claim byte-reproducible builds at v1. What we will
do instead is publish the release signing-certificate SHA-256 fingerprint in the
repository and on each Release, so a sideloaded build can be verified as ours.
Reproducible builds (pinned NDK, `SOURCE_DATE_EPOCH`, deterministic zip entries) are
a stretch goal with the same trigger as F-Droid.

### Supply-chain hygiene

- Official actions (`actions/*`, `pnpm/action-setup`, `actions/setup-java`) pinned to
  a major tag; **third-party actions pinned by full commit SHA** and updated by
  Dependabot with a review round, because a compromised third-party action on a
  release job holds the signing key.
- No `curl | bash` in workflows except the pinned Maestro installer, and the
  installer's version is an explicit input rather than "latest".
- Build logs are uploaded as artefacts with a secret-scrubbing step; `fastlane`
  runs with `--verbose` off in release jobs so no token echo lands in a log.

## Consequences

**Positive**

- One place builds both platforms, on runners we do not pay for, with the store
  credentials reachable from exactly one job in one environment.
- Every artefact a reviewer needs (screenshots, APK, simulator build, mock-relay
  report) is attached to the pull request automatically — which is what makes the
  review and QA gates in `AGENTS.md` practical rather than aspirational.
- The version scheme cannot drift: it is derived, not remembered.

**Negative**

- We own the native build configuration ourselves (Gradle, Xcode, prebuild), so
  Expo SDK upgrades can require pipeline work rather than a button.
- macOS runner minutes are the pipeline's bottleneck; a busy week of PRs to native
  code will queue.
- Signing-key custody is a human responsibility that the repository cannot enforce.

## Open risks

| Risk | Mitigation |
|---|---|
| Apple raises the SDK floor again (an Xcode 27 requirement is plausible within a year — an Xcode 27 / macOS 27 runner image already exists) | Treat the runner image and Xcode version as pinned inputs in one place; the upgrade is then a one-line change with a test build |
| Google raises `targetSdk` yearly | Keep `expo-target-sdk`/`expo-build-properties` in one config block and add a CI assertion that the built AAB's `targetSdkVersion` meets the current floor |
| Emulator/simulator flakiness blocking merges | One retry, high-value flows only, and the native jobs are advisory for docs/JS-only pull requests by explicit `if:` rather than by path filter |
| Expo SDK upgrade breaking `prebuild` determinism | The no-diff assertion on `expo prebuild --clean` runs on every native job |
| A leaked `PLAY_SERVICE_ACCOUNT_JSON` or keystore | Secrets only on `push`/`tag` jobs, fork guard, release environment, and a documented rotation procedure for each credential |
| Losing the Android keystore | Offline backup is documented as a maintainer duty; the alternative (new application id) is stated in the README |

## What would change this decision

- **EAS Build's free tier growing, or the project gaining a budget**, which would
  make the hosted-build path cheaper than maintaining Gradle/Xcode configuration.
  The switch is cheap: keep the same `fastlane` uploads, point them at EAS-produced
  artefacts.
- **GitHub changing the free-runner policy for public repositories**, which would
  make EAS Build — or a self-hosted Mac mini in CI — the only affordable option.
- **A second maintainer taking release duty**, which would move the release job from
  a single `release` environment to a tag-protected workflow with required review.
- **F-Droid acceptance becoming a goal** (rather than a nicety), which would force a
  `foss` flavour, a notification-free build, and a reproducible-build effort — a
  milestone, not a task.
