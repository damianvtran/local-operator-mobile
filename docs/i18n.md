# Internationalization

The app renders every user-facing string from a catalogue. English is the source
and just another catalogue: there is no path that puts a literal on screen. The
policy and its gates are in [`AGENTS.md`](../AGENTS.md),
"Internationalization: mandatory policy"; this page is the HOWTO.

Two questions are deliberately separate, and the code keeps them apart:

| Question | Answer lives in | Means |
| --- | --- | --- |
| What can this build render **today**? | `SHIPPED_LOCALES` (`src/i18n/locale.ts`) | A locale with a catalogue the runtime loads. Anything else renders English source. |
| What must the next change be **translated into**? | `SUPPORTED_LOCALES` (same file) | The programme's language set, and nothing more. Whether a key must reach a given locale is decided by the next row. |
| Which locales does CI hold a key to? | A catalogue **directory** under `src/i18n/catalogues/` | `generate.ts` compares every locale that has a directory with `en`, key for key. A supported locale with no directory is not compared; a key added to `en` alone is green until that locale ships. |

`SUPPORTED_LOCALES` mirrors the core repository's `i18n/languages.json` (`en` is
the source, the rest are supported). It is not maintained independently: a
language that is not in that manifest has no translator context, style guide or
audit trail, so it does not belong here.

## What ships today

`en`, `fr`, `es`, `zh-CN`, `ru`, `vi` and `hi`. `NOT_YET_SHIPPED_LOCALES` lists the supported
locales this build has no catalogue for, and English source stands in for all of them — no key, no empty
string, and no second preference. `src/i18n/__tests__/locales.test.ts` fails when
a supported locale is neither shipped nor in that pending list, so adding a
language to `SUPPORTED_LOCALES` is a decision with a diff, not a silent one.

## Add a string

1. **Pick the namespace.** One file per namespace: a new area is a new
   `src/i18n/catalogues/en/mobile.<area>.json`; an existing area's keys go into
   its current file. Do not create a namespace for one sentence.
2. **Pick the key.** The namespace is the file stem, so the key is
   `<namespace>.<name>` or, when the namespace has clusters of related keys,
   `<namespace>.<group>.<name>`; both are legal and the group is optional.
   Every segment is lower_snake_case and at most one group is allowed:
   `mobile.schedules.count.wakes` or `mobile.account_routing.reload`, not
   `mobile.schedules.3` and not `mobile.home.a.b.c`. **Mirrored copy is the one
   exception:** the `relay.*` catalogues are the desktop relay's own strings,
   copied key for key so a later adoption of the core locale files is a file
   copy rather than a translation pass, and the core's shape runs deeper than
   one group (`relay.chrome.session.subtitle.not_answering`). Their depth is
   therefore free; their prefix, segment syntax and non-empty remainder are
   still enforced, and the exemption cannot leak into an ordinary namespace.
   `generate.ts` fails a key
   that does not start with its file's namespace, or has a bad shape
   (`scripts/i18n/key-shape.ts`). The key is already fully qualified because the
   namespace is a file-layout and review-boundary decision, not a second
   argument to `t()`. Renaming a key later is a
   translation that must be redone everywhere, so name it for meaning, not for
   the wording of one draft.
3. **Write the English value** in that file. ICU messages only; values and
   plurals are placeholders, never concatenated sentences:

   ```json
   "mobile.schedules.count.wakes": "{count, plural, one {# wake} other {# wakes}}"
   ```

4. **Add translator context** to the sibling `mobile.<area>.context.json` under
   the same key. Every key needs one; generation fails without it.

   ```json
   "mobile.schedules.count.wakes": {
     "role": "meta",
     "note": "Wake count badge. {count} counts rows, not conversations. No final full stop."
   }
   ```

   `role` is one of `heading`, `help`, `status`, `button`, `confirm`, `meta`.
   The note is what a translator cannot guess: what the value counts, which
   sentence wins when two apply, what the text must not imply.
5. **Call it**, typed, from the public surface:

   ```ts
   import { t } from "@/i18n";

   t("mobile.schedules.heading")            // no placeholders: no second argument
   t("mobile.schedules.count.wakes", { count: wakes.length })
   ```

   `tsc` rejects an unknown key, a misspelled one, a missing or extra argument
   and a wrongly typed one, so the call site cannot drift from the catalogue.
   Never import a file inside `src/i18n/` directly; `src/i18n/index.ts` is the
   contract.
6. **Regenerate and check:**

   ```sh
   npm run -s i18n:generate        # writes src/i18n/catalogue.gen.ts
   npm run -s i18n:check           # what CI runs
   ```

   Commit the generated file with the catalogue change. It is generated from the
   JSON authoring source and `--check` fails when the two disagree, so a
   hand-edited projection is a red build rather than a quiet divergence.
7. **Translate into every shipped locale.** `generate.ts` compares every locale
   with a catalogue directory against English, so a new key is not done until it
   exists in each of them; a supported locale with no directory is not compared
   until it ships.

## Placeholders, ICU and technical text

- **Preserve the message exactly.** Placeholders, ICU plural and select arms and
  the source's structure survive translation unchanged. A translation that drops
  an argument, renames one or rewrites an arm fails generation, and one that
  keeps the syntax but changes the meaning is an audit finding.
- **No manual bidi control characters** in a catalogue value, in any locale.
  Direction is a layout property, not a string property; an invisible `U+202B`
  in source text is unreviewable and breaks searching.
- **Technical tokens stay English and untranslated:** commands, flags, paths,
  hostnames, model names, tool names and identifiers. They appear inside ICU
  messages as plain text and are copied through verbatim.
- **Developer diagnostics are not copy.** An exception message, a log line or an
  invariant states a fact for whoever reads the code; it stays English and it is
  not keyed.

## Add a locale

A directory is not activation. `catalogues.test.ts` compares the catalogue
directories with `SHIPPED_LOCALES`, so a translation that lands without passing
its audit is a red test rather than a locale that looks shipped.

1. **Confirm the language is supported.** It must be in `SUPPORTED_LOCALES` and
   in the core repository's `i18n/languages.json`. If it is absent there, this is
   a product decision to raise, not a locale to add here.
2. **Translate with an LLM translator agent — never a translation API or SDK.**
   No vendor client, no machine-translation CLI, no HTTP call to a service: the
   glossary, the per-key context notes and the audit trail have to be reviewable
   in the pull request, and a vendor response is none of those. One agent
   translates `src/i18n/catalogues/<tag>/` namespace by namespace.
3. **Audit independently.** A DIFFERENT agent — never the translator — reads the
   catalogue against the English source and the context notes and reports
   findings; the pull request records that report. Only a passing audit may flip
   the shipped set.
4. **Land the files.** `src/i18n/catalogues/<tag>/mobile.<area>.json` for every
   namespace: `generate.ts` fails when a namespace is missing, when a key is
   missing, or when a key English does not define appears.
5. **Wire it — this is the part the runtime does not do for you yet.** The
   generator projects the ENGLISH source into `src/i18n/catalogue.gen.ts` and
   `catalogues.ts` maps only what that projection carries, so a new locale needs
   the projection extended (or a JSON loader added for non-English locales) and
   an entry in `CATALOGUES`. Then add the tag to `SHIPPED_LOCALES`, remove it
   from `NOT_YET_SHIPPED_LOCALES`, and regenerate.
6. **Check width.** Translation is not a width-neutral change: French and Russian
   run longer than English, and Urdu shapes differently. Re-capture the screens
   at the smallest supported phone width and look for truncation, clipped rows
   and buttons that no longer fit, plus the RTL pass below.
7. `npm run -s i18n:check`, `npm test`, and a rendered before/after in the pull
   request.

The tag is BCP-47 and canonical (`zh-CN`, `ur`, `pt-BR`), because the manifest
value is compared with what `normalizeLocaleTag` produces from the relay's tag.
`locales.test.ts` fails a manifest entry the normalizer would rewrite.

The backend owns the language. `src/i18n/locale.ts` reads the resolved tag from
the relay's config frame; there is no phone-local preference, and nothing here
should add one.

## Urdu and right-to-left

`src/i18n/direction.ts` resolves direction from the ACTIVE catalogue — an Urdu
preference this build cannot render is laid out left-to-right, because laying
English out RTL is worse than not mirroring. Today only `ur` can answer `rtl`.

**What is wired now** (the layout half lands before the `ur` catalogue, so no
shipped locale changes a pixel):

- **The root direction.** `app/_layout.tsx` subscribes to the relay's config frame
  and puts the answer on the root view (`DirectionView`) as a Yoga `direction`
  style, which applies immediately — `I18nManager.forceRTL` is deliberately NOT
  used, because it needs an app restart and the language arrives live.
  `DirectionView` also sets the `dir` PROP: react-native-web resolves
  `start`/`end`/`marginEnd`/`paddingStart` in INLINE style objects from its own
  locale context, which only a `dir`/`lang` prop sets (neither a `direction`
  style nor `<html dir>` does), so without it `style={{ end: 0 }}` stays on the
  right in an RTL session. CSS-class utilities (`ps-*`, `border-s`) follow the
  style either way.
- **The web document.** `src/ui/direction.tsx` writes `dir` and `lang` onto
  `document.documentElement`. That is what carries the direction into portalled
  modals (react-native-web mounts them under `document.body`, outside the root
  view) and what makes an exported build checkable: a capture can assert
  `document.documentElement.dir` rather than inferring direction from pixels.
- **Modals** re-apply the direction on their own root (`Sheet`, `Dialog`, again
  through `DirectionView`), because a React Native `Modal` is a separate view
  root.
- **Logical edges.** `pl-/pr-`, `ml-/mr-`, `left-/right-`, `text-left/right`,
  `border-l/r`, plus the `marginLeft`-style props, are `ps-/pe-`, `ms-/me-`,
  `start-/end-`, `text-start` / `TEXT_END_CLASS`, `border-s/e` and
  `marginStart/End` across the audited sites. Trailing text alignment is the one
  that is NOT a plain logical class: web `text-end` follows the direction, but
  React Native has no `end` (it logs and falls back to the LEADING edge, which
  would left-align a right-aligned column in English), while native `right` is
  already the trailing edge because RN swaps left/right itself under an RTL layout.
  `TEXT_END_CLASS` (`web:text-end native:text-right`) is the one definition. In a left-to-right layout a logical utility resolves to the same
  physical edge it replaced, which is why the sweep changes no LTR pixel.
  `src/i18n/__tests__/physical-edges.test.ts` FAILS on a new physical edge
  anywhere in `src/**` or `app/**` unless it is on a short, commented allowlist
  with a reason and an exact occurrence COUNT per entry. It strips comments as
  spans (so code after a comment on the same line is still scanned) and covers
  `pl/pr/ml/mr-*` including `-px` and arbitrary values, `left/right-*`, `inset-x`,
  `space-x`, `rounded-{t,b}{l,r}`, `float-*`, `row-reverse`, `translateX`,
  numeric/constant/inset `left:`/`right:` style props and `textAlign` literals.
  Its documented limits: a COMPUTED inset (`left: x + 1`), a physical value built
  at runtime into a class name, and `marginHorizontal`/`inset-x-*` (symmetric, and
  allowlisted where they are).
- **Mirrored affordances.** `src/ui/components/back-icon.tsx` is the one back
  glyph: an arrow (or chevron) that points at the reading start, so it flips to
  the right in RTL. Not mirrored, on purpose: the brand mark, media transport
  (`Play`), object icons (`Laptop`, `Server`, `Mic`, `Bell`) and vertical
  disclosure chevrons.
- **Mixed content.** Code blocks (`markdown.tsx`), command blocks
  (`command-block.tsx`) and diagnostic values (`settings.tsx`) carry
  `writingDirection: "ltr"` (with `textAlign` `left` on web and `auto` on native
  where the block owns its line: RN swaps `left`/`right` itself under an RTL
  layout, so a literal native `left` would land on the right; `auto` follows
  `writingDirection` on iOS and web, but Android ignores `writingDirection` for
  `<Text>`, so a command or code block may still sit on the physical right there)
  via `LTR_TEXT`/`LTR_WRITING` in `src/ui/direction.tsx`. The isolation is at the
  component, never a control character in the catalogue.

  **Known, unverified gap:** that Android behaviour is reasoned from React Native's
  own source and has **not** been seen on a device — no simulator is available
  where this was written, and the Android end-to-end workflow takes no language
  input, so it cannot capture an RTL frame yet. Everything else about the RTL
  layout is measured on the web export, which cannot demonstrate an Android-only
  defect. Treat "LTR-isolated blocks inside RTL paragraphs on Android" as
  unconfirmed until someone captures that frame; adding a language input to the
  Android workflow is the change that would let CI produce it.

**What is NOT wired, and why:**

- **The conversations drawer** is anchored to the physical left edge and slides
  with a physical `translateX`. Flipping the anchor without flipping the animation
  would slide it in from the wrong off-screen side, so it stays physical and is
  the guard's one allowlisted holdout — an RTL design round owns it.
- **The table's scroll cues** (`markdown.tsx`): the fade is now chosen on a
  logical edge and painted on the resolved physical one, but the overflow state it
  reads comes from physical scroll metrics (`contentOffset.x`). In RTL the
  browser moves the scroll origin, so the "more content ahead" cue is mapped in
  reading order rather than measured — the one behaviour to re-measure against a
  real RTL frame.
- **Native layout is unverified here.** This host has no simulator, so the native
  half of the above is reasoned from React Native's own layout source and is
  covered only by CI's native build, not by a rendered frame.

A native surface can and cannot do different things:

- **Can mirror:** text alignment and writing direction, logical spacing
  (`marginStart`/`paddingEnd`), chevrons and directional affordances, and the
  order of leading/trailing chrome.
- **Cannot mirror, and must not try:** marks and imagery whose direction is
  semantic (brand marks, media transport, icons that depict a physical object),
  and any layout written with hard-coded `left`/`right` — those have to be
  converted to start/end first, or one locale silently inverts the other.
- **Cannot be inferred:** the direction of a translated string. Mixed content —
  hostnames, paths, command snippets, model names — keeps its own direction and
  needs explicit isolation at the component that renders it, not a control
  character in the catalogue.

## What this page does not cover

Live re-render on a language change. The keyed copy modules export their
strings as constants, so those values resolve once at import; functions that call
`t()` re-resolve per invocation. Converting the constants to a hook is a screen
rewrite that belongs to the wave that lands translations, and the runtime's
header documents that boundary.
